Abstract

flood-fill-cuda recolors every red blob in an image on the GPU, in Python with Numba CUDA. It starts from a plain CPU breadth-first search (BFS). Six chapters then rebuild it, each one answering the weakness the previous one measured.

Chapters 1 to 3 spread one BFS over one block, then two blocks, then the whole GPU. Chapter 4 fills two blobs in one launch. Chapter 5 finds every blob by itself: 755,577 blobs in 24.8 ms on a 16-megapixel noise image, with no seeds given.

Chapter 6 changes the unit of work. A run is an unbroken stretch of red pixels in one row. The 81-megapixel test image, input_blobs.png, holds 13.45 million red pixels but only 539,207 runs.

Labeling runs instead of pixels cuts chapter 5's 58.51 ms to 2.96 ms from RGB. If the image is already packed to one bit per pixel, it takes 1.46 ms.

Every kernel is checked pixel for pixel against a CPU reference. Every timing comes from a committed benchmark file, and the page shows where the GPU loses too. Memory sets the floor: reading the 243 MB RGB image once costs 1.14 ms.

Six Chapters, One Chain

Each chapter starts from a weakness the one before it measured. The second column names it. All times are kernel times, with the input already on the GPU.

Chapter What the last chapter left open What it built Headline
1. One block One CPU core is serial. Level-synchronous BFS in one block, with a shared-memory ring and a global spill tier. 1.8-2.0× compiled CPU code (@njit) on a 36 Mpx blob, across two runs.
2. Two blocks One block uses one SM (streaming multiprocessor), 4% of the GPU. Two blocks and three ways to share one wave: by space, by one global queue, by direction. 2.10× chapter 1 at 36 Mpx. The plain global queue won.
3. N blocks Two blocks use two SMs, 8%. One cooperative grid across all 24 SMs, grid-wide barriers, then 8-connectivity. 64 Mpx in 100.3 ms. Registers cap the timed kernel at 512 threads per SM; a leaner twin without counters fits 768.
4. Two blobs Each launch fills one blob. Two blobs in one launch. The label rides in a spare bit of each queue entry. 1.05-2.05× faster than two back-to-back launches (median, four scenes).
5. N blobs The caller must supply the seeds. Seedless discovery: candidate waves plus an atomicMin union-find. 755,577 blobs in 24.8 ms on 16 Mpx of noise, one launch, no seeds.
6. N runs Every kernel still moves pixels. Run-based labeling: pack the image to one bit per pixel, then six plain kernels. 58.51 ms to 2.96 ms from RGB, or 1.46 ms from a packed mask, on the 81 Mpx image. Same session.

The CPU walks, the GPU sweeps

The same 8000 × 8000 square, filled by one CPU core and by the GPU of chapters 1 to 3, on one shared clock. Each lane stops at the time measured for it in one benchmark session; the fill in between is modeled.

One block is only 1.9× faster than the CPU, and two blocks 3.9×. With all 24 SMs the GPU finishes in 134 ms, 15.3× faster than the CPU's 2,041 ms.

The video plays 6× slower than real time. GPU lanes show kernel time; the CPU lane is the whole call, allocation included.

Size matters. At a million pixels one block is still slower than the CPU (0.75-0.81×), and it wins in every committed run only from 16 million pixels.

Runs, Not Pixels

A run is one unbroken span of red inside a row. The 9000 × 9000 test image has 81 million pixels and 13.45 million red ones, but only 539,207 runs. That is 25× fewer things to label, with the same information.

Chapter 6 accepts the image in two forms, called contracts. With RGB in, it first packs the image to one bit per pixel. With a packed mask in, the caller already holds that mask.

Six plain kernels then run in stream order. Only pack and paint touch the RGB image. The five labeling kernels between them take 0.64 ms in the RGB run.

Blob shape matters much less now. A BFS needs one level per step along a winding corridor: chapter 3 took 32,641 levels on a 256 × 256 serpentine. Chapter 6 has no levels at all.

On a 2048 × 2048 serpentine it takes 0.47 ms from a packed mask, 39.9× faster than chapter 5. The smallest gains are 3.3× on input_blocks.png, a 1-megapixel image, and 4.0× on pixel-level noise with about 1.4 pixels per run.

Every Stage on the Same Image

Every stage ran on the same image, input_blobs.png: 81 million pixels and 2,522 red blobs.

Pure Python, given the seeds, needs 24,083 ms. Compiled CPU code (Numba @njit) needs 1,346 ms. Chapter 6 needs 2.96 ms from RGB, or 1.46 ms from a packed mask.

The Memory Wall

The RGB image is 243 MB. Reading it once at the measured read peak of 212.6 GB/s takes 1.14 ms. So at the best read rate measured here, the RGB input alone costs more than a millisecond.

A packed mask skips that read. On crops of the real image, which roughly keep its run length, red fraction and blob sizes, the packed-mask pipeline stays under 1 ms out to about 50 megapixels. The full 81 megapixels take 1.46 ms.

How the Numbers Were Measured

  • One machine: an NVIDIA GeForce RTX 4060 Laptop GPU with 24 SMs, under WSL2.
  • Correctness comes first. Every kernel is checked against a CPU reference built with Numba @njit. The tests compare depth maps or label maps, not pixel counts.
  • Times are kernel times, with the input already on the GPU. Copies and allocation are not included.
  • Chapters 1 to 5 time the launch and synchronize on the host. Chapter 6 uses CUDA events after a clock warm-up (8 s per scene, 4 s per crop in the size sweep).
  • Results drift between sessions on this laptop: chapter 5 on input_blobs.png read 51.03 ms in one session and 58.51 ms in another. So every comparison pairs numbers from one session where it can.
  • Every result is a committed JSON file under src/flood_fill_cuda/results/.

Related Links

Breadth-first search on the GPU goes back to Harish and Narayanan (2007). Merrill, Garland and Grimshaw (2012) show how much redundant work a 2D lattice causes without duplicate culling. That is why chapters 1 to 5 claim a pixel before they enqueue it.

The enqueue in chapters 2 to 5, and in chapter 1's spill variant, uses warp-aggregated atomics: one atomic per warp instead of one per thread. The persistent kernels of chapters 2 to 5 wait on Numba's cooperative groups grid barrier.

Connected-component labeling on the GPU has a long line of work: Hawick, Leist and Playne (2010), Stava and Benes (2011), and Playne and Hawick (2018). The block-based BUF and BKE algorithms of Allegretti, Bolelli and Grana (2020) belong to it too. Chapter 5's union-find follows this line.

Labeling runs instead of pixels is a classic CPU idea, described by He, Chao and Suzuki (2008). Chapter 6 applies it on the GPU.

Chapter 6 skips the decoupled look-back scan of Merrill and Garland (2016). There are too few rows for a multi-block scan to pay.

Every kernel is written in Python with Numba for CUDA GPUs.
