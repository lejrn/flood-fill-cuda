Abstract

flood-fill-cuda recolors every red blob in an image on the GPU, in Python with Numba CUDA. It starts from a plain CPU breadth-first search. Six chapters then rebuild it, each one answering the weakness the previous one measured.

Chapters 1 to 3 spread one BFS over one block, then two blocks, then the whole GPU. Chapter 4 fills two blobs in one launch. Chapter 5 finds every blob by itself: 755,577 blobs in 24.8 ms, with no seeds given.

Chapter 6 changes the unit of work. The 81-megapixel test image holds 13.45 million red pixels but only 539,207 runs. Labeling runs instead of pixels cuts the time from 58.51 ms to 2.96 ms from RGB, or 1.46 ms from a packed mask.

Every kernel is checked pixel for pixel against a CPU reference. Every number on this page comes from a committed benchmark file, and the losses are reported next to the wins. At the end, memory sets the floor: reading the 243 MB RGB image alone costs 1.14 ms.

Six Chapters, One Chain

Each chapter answers the weakness the previous one measured. The question in each row is what the chapter before it left open.

Chapter The open question What it built Headline
1. One block One CPU core is serial. Level-synchronous BFS in one block, with a shared-memory ring and a global spill tier. 1.8-2.0× compiled CPU code on a 36 Mpx blob (kernel time).
2. Two blocks One SM is 4% of the GPU. Two blocks and three ways to share one wave: by space, by one global queue, by direction. 2.10× chapter 1 at 36 Mpx. The plain global queue won.
3. N blocks Two SMs are 8%. One cooperative grid across all 24 SMs, grid-wide barriers, then 8-connectivity. 64 Mpx in 100.3 ms (kernel time). Registers cap the grid at 512 threads per SM.
4. Two blobs One blob is one BFS. Two blobs in one launch. The label rides in a spare bit of each queue entry. 1.05-2.05× two back-to-back launches.
5. N blobs Who finds the seeds? Seedless discovery: candidate waves plus an atomicMin union-find. 755,577 blobs in 24.8 ms on 16 Mpx of noise, one launch, no seeds.
6. N runs Why move pixels at all? Run-based labeling: pack the image to one bit per pixel, then six plain kernels. 58.51 ms to 1.46 ms on the 81 Mpx image, same session.

Runs, Not Pixels

A run is one unbroken span of red inside a row. The 9000 × 9000 test image has 81 million pixels and 13.45 million red ones, but only 539,207 runs. That is 25× fewer things to label, with the same information.

Chapter 6 packs the image to one bit per pixel, then runs six plain kernels in stream order. Only the first and the last step touch pixels. Everything between them, the whole connected-components problem over 539k runs, takes 0.64 ms.

Blob shape stops mattering. The serpentine that cost chapter 3 tens of thousands of BFS levels now takes 0.47 ms, 39.9× faster than chapter 5. The weak case is 1-pixel noise, about 1.4 pixels per run, where chapter 6 is only 4.0× faster.

Every Stage on the Same Image

One picture went through every stage: input_blobs.png, 81 million pixels, 2,522 red blobs. Pure Python needs 24,083 ms. Compiled @njit needs 1,346 ms. Chapter 6 needs 1.46 ms from a packed mask, or 2.96 ms from RGB.

The Memory Wall

The RGB image is 243 MB. Just reading it at the measured read peak of 212.6 GB/s takes 1.14 ms. So on this laptop GPU, nothing recolors this image from RGB in under a millisecond. Only the packed-mask contract gets there.

Crops of the real image keep its run length, red fraction and blob sizes. On them the packed-mask pipeline stays under 1 ms out to about 50 megapixels.

How the Numbers Were Measured

  • One machine: an NVIDIA GeForce RTX 4060 Laptop GPU with 24 SMs, under WSL2.
  • Correctness first. Every kernel is compared with a CPU reference built with Numba @njit, and the tests compare depth maps or label maps, not pixel counts.
  • Times are kernel times with the input already on the GPU. Copies and allocation are not included.
  • Chapters 1 to 5 time the launch and synchronize on the host. Chapter 6 uses CUDA events after an 8 s clock warm-up.
  • This laptop's clocks drift by about 8-10% between sessions, so every comparison pairs numbers from one session where it can.
  • Every result is a committed JSON file under src/flood_fill_cuda/results/.

Related Links

Breadth-first search on the GPU goes back to Harish and Narayanan (2007). Merrill, Garland and Grimshaw (2012) show how much redundant work a 2D lattice causes without duplicate culling. That is why every chapter here claims a pixel before it enqueues it.

The enqueue in chapters 1 to 5 uses warp-aggregated atomics, one atomic per warp instead of one per thread. The persistent kernels of chapters 2 to 5 wait on Numba's cooperative groups grid barrier.

Connected-component labeling on the GPU has a long line of work: Hawick, Leist and Playne (2010), Stava and Benes (2011), Playne and Hawick (2018), and the block-based BUF and BKE algorithms of Allegretti, Bolelli and Grana (2020). Chapter 5's union-find follows this line.

Labeling runs instead of pixels is a classic CPU idea; see He, Chao and Suzuki (2008). Chapter 6 applies it on the GPU. It also skips the decoupled look-back scan of Merrill and Garland (2016): there are too few rows for a multi-block scan to pay.

Every kernel is written in Python with Numba for CUDA GPUs.
